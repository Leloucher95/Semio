# Semio — Instructions permanentes pour Claude Code

## Mission
Application web en français : tâches réutilisables, semaine type, plan mensuel indépendant, suivi de chaque jour, impression A4. Livrer **vite et bien**, en tranches verticales testées, pas en prototypes non connectés. Référence produit : `docs/CAHIER-DES-CHARGES-ORIGINAL.md` ; ajustements techniques documentés dans `docs/ARCHITECTURE.md` ; exécution : `PROMPT-MAITRE-AGENT.md`.

## Contraintes immuables
- Vue 3 + Vite + TypeScript strict + Pinia + Tailwind CSS 4 + Vue Router; français uniquement V1.
- Go + PocketBase **librairie Go**, migrations Go versionnées, SQLite; pas de hooks JS, d'ORM ou de backend Node.
- Déploiement défini par le brief : binaire unique `embed.FS` + systemd + reverse proxy. **Ne pas introduire Docker en production** sans instruction contraire.
- Dates de suivi = `YYYY-MM-DD` en timezone de l'utilisateur, jamais UTC; défaut `Africa/Porto-Novo`. Créneaux = minutes depuis minuit, jour ISO 1–7, pas de 30 minutes.
- Modèle et plan mensuel sont distincts. Snapshot des tâches/objectifs/placements dans le plan. Jamais de suppression physique des tâches référencées : archivage.
- Toutes les collections métier sont tenant-scopées par `owner`, API rules explicites **ET** validation serveur des relations. Ne jamais utiliser une simple règle owner comme protection suffisante.
- Aucune clé/secrète en git, aucun upload utilisateur V1, aucun stockage de fichiers utilisateurs sur le VPS.
- Drag grille maison Pointer Events + alternative formulaire accessible. Aucun SortableJS pour les blocs horaires.

### Identité Git et attribution des commits

- Tous les commits doivent être attribués exclusivement au propriétaire du dépôt, en utilisant son identité Git déjà configurée.
- Ne jamais modifier `user.name` ou `user.email` dans la configuration Git locale ou globale.
- Ne jamais ajouter de ligne `Co-authored-by`, `Signed-off-by` ou `Contributed-by` mentionnant Claude, Anthropic, une IA ou un autre contributeur.
- Ne jamais utiliser `--author` ou `--reset-author` pour substituer une identité.
- Ne jamais ajouter de mention du type « Generated by Claude », « AI-assisted » ou « Created with Claude Code » dans les messages de commit.
- Ne jamais modifier `.mailmap` ou créer de métadonnées destinées à attribuer des contributions à l'agent.
- Avant le premier commit, vérifier `git config user.name` et `git config user.email`. Si l'identité est absente ou incorrecte, demander au propriétaire de la configurer.
- Les commits doivent contenir uniquement un message descriptif et conventionnel, par exemple `feat: implement weekly planner`.
- Cette règle s'applique à tous les commits, y compris ceux créés par les sous-agents et les skills.

`.claude/settings.json` désactive l'attribution automatique (`attribution.commit` et `attribution.pr` vides).

## Réflexes de développement
1. Au début d'une tranche : lire les fichiers concernés, `PROGRESS.md` et les tests associés. Si besoin, invoquer `/livrer-slice`.
2. Implémenter le chemin utilisateur de bout en bout. Écrire d'abord des tests sur règles délicates (dates, chevauchements, sécurité, snapshots, opérations transactionnelles).
3. Faire le minimum d'abstraction : fonctions pures, modules simples; éviter microservices, DDD cérémoniel, surinfrastructure et généralisation prématurée.
4. Après une modification : exécuter les tests ciblés et corriger. Avant de finir une phase : vérifier Go, Vitest, TS et E2E associés. **Ne jamais annoncer PASS sans commande exécutée.**
5. Mettre à jour `PROGRESS.md` (fait, vérifié, restant); nouvelles décisions en une ligne dans `DECISIONS.md`.
6. Installer dépendances stables et versionnées; lire la documentation PocketBase correspondant à la version exacte de `go.mod`.
7. Utiliser des données de test isolées. Ne rien déployer/effacer sur le VPS de prod sans autorisation.

## Conventions utiles
- Front : `frontend/src/views` pages, `components` présentation, `stores` état, `composables` interactions, `lib` calculs purs, `print` CSS.
- Back : `backend/migrations`, `internal/security` propriétaire+relations, `internal/planning` transactions, `internal/domain` calendrier, `internal/web` SPA embedding.
- Backend source de vérité persistante; Pinia reflète l'état distant et permet l'optimisme avec rollback.
- Les requêtes de création et mise à jour valident le propriétaire et les relations **côté serveur**, jamais uniquement via UI.
- Les intervalles sont semi-ouverts `[début, fin)` : deux créneaux adjacents ne se chevauchent pas.
- UI : agenda papier élégant, couleurs sobres, typographie locale et lisible, grilles et cases réelles; pas de design générique de dashboard IA.
- Pour print volumineux : ne jamais cacher de lignes; paginer si nécessaire.

## Commandes attendues après P0
- `make dev` : Go PocketBase + Vite avec proxy API (ou instructions équivalentes sur Windows).
- `make test` : go test + Vitest + typecheck.
- `make e2e` : Playwright Chromium.
- `make build` : build front → copie dans `backend/web/dist` → build binaire Go.
- `make verify` : test + E2E + build + smoke du binaire et des routes.
Si une commande n'existe pas encore, l'implémenter lors de P0, ne pas faire semblant de l'avoir exécutée.

## Garde-fous
- Échec de compilation/test ciblé = corriger avant d'empiler d'autres fonctionnalités.
- Modèle modifié après application = mois inchangé; la navigation de mois ne recalcule pas un modèle.
- Duplicate vers mois existant = erreur claire, aucune écriture partielle.
- Test isolation A/B et références externes obligatoire avant d'autoriser la V1.
- R2 non configuré : code fonctionnel, **publication production bloquée**, pas d'affirmation de sauvegarde valide.
